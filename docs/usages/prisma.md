# Prisma — Usage & Folder Guidelines

This document explains how Prisma is used in this starter kit, what the common Prisma files do, and recommended practices for organizing Prisma schemas for a TypeScript + Express + MongoDB starter.

## What is Prisma (brief)

Prisma is an ORM/DB toolkit that provides:
- A declarative schema language for defining models.
- A generated TypeScript client to interact with the database.
- CLI tools for schema sync (db push / db pull), client generation and seeding.

In this kit Prisma is configured for MongoDB (see `prisma/schema/schema.prisma`).

## Why use Prisma in this starter

- Strong TypeScript client and type-safety.
- Cleaner data-access code (no manual mapping).
- Quick prototyping with `prisma db push` / introspection with `prisma db pull`.

## Folder layout (recommended)

prisma/
- schema/                 -> Directory holding the final `schema.prisma` or schema fragments
  - schema.prisma         -> The assembled Prisma schema used by the CLI
  - models/               -> Optional: model fragments (one file per model) — see merge script
- seed.ts                 -> Optional seeding script (runs with ts-node)
prisma.config.ts          -> Local Prisma config used by the project (TypeScript)

`docs/usages/prisma.md`  -> This documentation

## Key files explained

- `prisma/schema/schema.prisma`
  - The canonical Prisma schema file. Contains datasource, generator and model definitions.
  - Example (in this project it currently contains the datasource for MongoDB).

- `prisma.config.ts`
  - Project-level helper for custom Prisma CLI configuration or local scripts.
  - In this repo `prisma.config.ts` sets schema path or other Prisma-related TypeScript configuration used by tooling.

- Models as separate files (optional)
  - Prisma does not natively import other `.prisma` files. If you prefer modular model files (one file per model), keep them under `prisma/schema/models/` and use a small script to concatenate them into `prisma/schema/schema.prisma` before running Prisma CLI commands.
  - This keeps large projects maintainable.

## Why split models across files?

- Easier to manage when schema grows.
- Each domain/entity can live in its own file for reviews and git history.
- Avoids one huge file — improves developer experience.

Note: The Prisma CLI requires a single schema file. Splitting requires a build/merge step.

## Recommended workflow & commands

Install / update Prisma:

```bash
npm install prisma @prisma/client --save-dev
```

Generate the client (after schema is prepared):

```bash
npx prisma generate --schema=prisma/schema/schema.prisma
```

Push schema to DB (for MongoDB):

```bash
npx prisma db push --schema=prisma/schema/schema.prisma
```

Introspect an existing DB (pull):

```bash
npx prisma db pull --schema=prisma/schema/schema.prisma
```

Run seed script (example):

```bash
node --loader ts-node/esm prisma/seed.ts
# or use a dedicated npm script for ts-node
```

Test authentication / client usage from code:

```ts
import { PrismaClient } from "@prisma/client";
const prisma = new PrismaClient();
// use prisma.user.findMany() etc.
```

## Example: keep schema modular (optional)

If you want to manage models in separate files, add a small script to merge fragments into the final `schema.prisma` before running Prisma commands.

Node merge script (example):

```js
// filepath: prisma/build-schema.js
const fs = require('fs');
const path = require('path');

const dir = path.join(__dirname, 'schema');
const out = path.join(dir, 'schema.prisma');
const header = fs.readFileSync(path.join(dir, 'header.prisma'), 'utf8'); // datasource + generator
const modelsDir = path.join(dir, 'models');

const parts = [header];
fs.readdirSync(modelsDir)
  .filter(f => f.endsWith('.prisma'))
  .sort()
  .forEach(f => {
    parts.push('\n' + fs.readFileSync(path.join(modelsDir, f), 'utf8'));
  });

fs.writeFileSync(out, parts.join('\n'));
console.log('Built', out);
```

Suggested schema layout for this approach:
- `prisma/schema/header.prisma`  -> datasource + generator blocks
- `prisma/schema/models/*.prisma` -> model fragments
- `prisma/schema/schema.prisma`  -> auto-generated by `prisma/build-schema.js`

Suggested npm scripts:

```json
"scripts": {
  "prisma:build": "node prisma/build-schema.js",
  "prisma:generate": "npm run prisma:build && npx prisma generate --schema=prisma/schema/schema.prisma",
  "prisma:db:push": "npm run prisma:build && npx prisma db push --schema=prisma/schema/schema.prisma",
  "prisma:db:pull": "npx prisma db pull --schema=prisma/schema/schema.prisma"
}
```

## Notes specific to MongoDB

- Prisma’s migration system is not fully supported for MongoDB. Use `prisma db push` to sync the schema or manage migrations externally.
- When using `schema.prisma` with MongoDB, be deliberate about indexes and relations: some relational features differ from SQL providers.

## Best practices

- Keep datasource credentials (`DATABASE_URL`) in environment variables and do not commit `.env` with secrets.
- Commit model fragments and the header, but ignore generated final schema if you prefer (or commit it to keep reproducible CI).
- Add `prisma generate` to your build/dev-start scripts so the client is always in sync.
